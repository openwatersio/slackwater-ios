# SSCOFS field spike — method + decision (2026-08-20)

Spike per `docs/superpowers/specs/2026-08-20-current-field-composite-design.md` §3: before
committing to the full backdrop pipeline (190-day corpus, full mesh), fit a 60-day corpus over
one box and score it against the same bar the app already ships (`spikes/chs-currents-fit`),
via the app's own shipping fit path. This spike ran to completion — full 2,004-pair matrix,
all files on disk under `results/`, `corpus/` (raw fetch, gitignored), `truth/`, `samples/`.

## Method

1. **Box.** Southern Gulf Islands + San Juans, `[-123.95, 48.30, -122.55, 49.25]`
   (1.33 deg²) — deliberately contains both a validated CHS gate at ratio 1.00 (Active Pass)
   and the #99 negative control at ratio 0.24 (Dodd Narrows). 73,550 of the SSCOFS mesh's
   433,410 elements fall inside it (~17%) — `mesh_subset.py`.
2. **Corpus.** 60 days of hourly SSCOFS nowcast surface u/v (24 valid times/day: 4 forecast
   cycles × 6 hourly steps), fetched via ranged HTTP reads of `noaa-nos-ofs-pds` S3 fields
   files — `fetch_corpus.py`, resumable, one `.npz` per day. Time-mapping (`cycle, step →
   valid time`) was verified against the file's own `Times`/`time` variables at both a zero
   and a non-zero offset (task-2-report), not just asserted from the formula.
3. **Truth stations.** `truth_stations.py`: CHS gates from IWLS (`wcp1-events` series) + NOAA
   type-H current stations from MDAPI, inside the box — **56 total** (6 CHS, 50 NOAA;
   `truth/stations.json`).
4. **Projection.** `signed = speed · cos(dir − floodDirection)` — the harness's own current
   projection (`main.swift:189`), the same formula `chs-currents-fit` uses. Applied per
   (station, nearby element) pair — every mesh element within 600 m of a truth station,
   `make_samples.py` — producing `samples/<slug>-e<i>.json` in `fitTides`'s exact input shape.
5. **Fit — the shipping path.** `tools/FitValidation` grew a `--samples`/`--events` file-input
   mode (Task 5) that joins the existing IWLS-fed harness at the JSContext setup: same
   committed `chs-bundle.js`/`chs-glue.js`, same `fitTides` call, same `CurrentStation`
   prediction/scoring code the live CHS-gate path uses — only the I/O (file vs. IWLS fetch)
   differs. **Byte-parity evidence:** file mode was verified against a live-fetched Dodd
   Narrows report — fit JSON identical field-for-field (offset, rms, 23 constituents, phases)
   on both windows, differing only in the JS-side wall-clock timing field (commit `91cb96d`,
   task-5-report.md). The negative-control and speed numbers below therefore come from the
   same code path that scores `spikes/chs-currents-fit`'s 30 shipped/rejected gates, not a
   parallel implementation.
6. **Windows.** The tool reports two windows, `210d` and `60d`, and its exit code follows
   `210d` (`main.swift`) — but this spike's corpus **is** 60 days, so both windows in every
   report here are fit from the same 1,440 hourly samples (confirmed on-disk, e.g.
   `results/dodd-narrows-e239685.json`: `"samples": 1440`, `"window": "210d"`). The `210d`
   label is inherited convention, not a longer fit, in this run. Every result carries
   `"unseparable": ["S2/T2","N2/NU2","2N2/MU2","S2/K2","K1/P1","MSF/MF","K2/T2"]` — at 60
   days those pairs (notably K1/P1) are below the Rayleigh criterion and get inference
   constituents rather than independent fits, exactly the mechanism spec §2 gives for
   requiring 190 days in Phase B.
7. **Score.** Held out against each truth station's own published events
   (`wcp1-events`/NOAA `MAX_SLACK`), +28..+35 days past the fit window — same held-out
   convention as `chs-currents-fit`. `run_matrix.sh` ran all 2,004 (station, element) pairs;
   `report.py` aggregated `results/*.json` (the tool's own structured report files, not a
   log-text regex) into `RESULTS.md`.

## The bar

Copied verbatim from `spikes/chs-currents-fit/README.md` — the bar this spec's §3 gate 1
cites as "the existing bar":

| Quantity | Bar | Why |
|---|---|---|
| Slack timing median | ≤ 15 min | the planning margin a skipper actually uses (arrive 15 early) |
| Slack timing worst | ≤ 30 min | one slack >30 min off is wrong water, whatever the median says |
| Extremum timing median | ≤ 20 min | the engine's established maxima bar |
| Peak speed median error | ≤ 0.5 kn | the number a skipper reads off the peak |
| Axis | no systematic flip | wrong-sign ≥60% of extrema quarantines |

PASS requires all five. `results/*.json`'s own `"pass"` field is this verdict, computed by
the same scoring code as the live CHS path — nothing in this README's aggregation recomputes it.

## Results — verified, not just quoted

Full per-station table (best + nearest element), element coverage, and coverage gaps:
**`RESULTS.md`** (generated by `report.py` from `results/*.json`, committed alongside this file).

Headline numbers, independently recomputed from `results/*.json` against `samples/index.json`
before writing this section (script below). `speedMedianKn: -1` is fit-validation's sentinel
for "no scoreable extremum" (every published extremum at that element was below its 0.75 kn
significance floor) — not a real error, so sentinel rows are excluded before picking each
station's best/nearest element:

```sh
python3 -c "
import json, glob, os
idx = json.load(open('samples/index.json'))
by_label = {f\"{r['slug']}-e{r['elem']}\": r for r in idx}
per_station = {}
for path in sorted(glob.glob('results/*.json')):
    label = os.path.basename(path)[:-5]
    if label not in by_label: continue
    r = json.load(open(path))
    row = {'slack_med': r['slackMedianMin'], 'speed_med': r['speedMedianKn'], 'pass': r['pass'], **by_label[label]}
    per_station.setdefault(row['slug'], []).append(row)
scoreable = {s: [r for r in rows if r['speed_med'] >= 0] for s, rows in per_station.items()}
unscoreable = [s for s, rows in scoreable.items() if not rows]
scoreable = {s: rows for s, rows in scoreable.items() if rows}
print('stations scoreable:', len(scoreable), '— unscoreable (all sentinel):', unscoreable)
best = {s: min(rows, key=lambda r: r['speed_med']) for s, rows in scoreable.items()}
print('five-bar PASS:', sum(r['pass'] for r in best.values()), '/', len(best))
print('speed-only PASS (<=0.5kn):', sum(r['speed_med'] <= 0.5 for r in best.values()), '/', len(best))
"
```

- **Truth stations:** 56 total (6 CHS + 50 NOAA). 2 never had a mesh element within 600 m
  (`gabriola-passage`, `tillicum-bridge` — `export.log`) and never reached `samples/index.json`.
  54 stations scored (2,004 pairs, `run_matrix.sh`/`report.py`), of which 1 (`cherry-point`,
  36/36 elements) is unscoreable — every published extremum at every nearby element is below
  the 0.75 kn significance floor, so `speedMedianKn` is the -1 sentinel on all 36 rows.
  **53 stations scoreable.**
- **Five-bar gate (the operative bar): 0/53 stations PASS** on their best element. Dominant
  failure is slack timing: median 13.3–111.6 min across stations' best elements, against the
  15-min bar — even the cleanest strong-current stations are ~10 min over (Deception Pass
  Narrows 25.4 min, Active Pass 25.7 min).
- **Speed-only reading (peak-speed median ≤ 0.5 kn alone): 40/53 pass** at best element. The
  13 failures: Dodd Narrows 3.72 kn (the negative control), Porlier Pass 2.79 kn, Deception
  Pass Narrows 1.60 kn, Race Passage 0.87 kn, Lawrence Point 0.75 kn, Saddle Bag Island Passage
  0.69 kn, and seven near-misses at 0.51–0.62 kn (Active Pass, Cattle Point 1.2 nm SE, both
  Discovery Island stations, Strait of Georgia 4.5 nm SW, Turn Point, Upright Channel Narrows).
- **Bundle:** density-extrapolating the box's element count to the full render region
  (Salish clip, 12.6 deg²) projects **~696,789 render-region elements** — more than the SSCOFS
  mesh's entire 433,410 elements, so it's an over-estimate of true render-region coverage.
  At that projected count: 23 constituents → **165.8 MB**, 12 constituents → **89.2 MB**.
  Capping the extrapolation at the full mesh instead scales both to **≈103 MB / ≈55 MB**.
  Either reading is over the 40 MB budget.

## Decision gates (spec §3)

**1. Do certifiable sub-regions meet the bar?** No. 0/53 scoreable stations pass the five-bar
table on their best-scoring element. Every failure fails on slack timing (13–111 min medians
vs 15 min); speed alone would pass 40/53, but the spec's bar is the five-quantity table, not
speed alone (see "Open question" below).

**2. Did Dodd-class stations correctly fail?** Yes — the gate rejects as designed. Dodd
Narrows: speed-median error 3.72 kn (best element) / 3.82 kn (nearest), 6–7× the 0.5 kn bar,
consistent across all 5 nearby elements — a decisive fail, not a near-miss. This is the
required negative-control outcome (§3: "the gate must prove it rejects, not only that it
accepts") and it holds.

**3. Extrapolated bundle ≤ 40 MB at which constituent count?** None. 165.8 MB at 23
constituents, 89.2 MB at 12 — both against the (over-estimated) density extrapolation; even
the full-mesh-capped floor (≈55 MB at 12 constituents) is still over budget.
(superseded for the certified region — see "Prerequisites executed" below: PASS at 13.25 MB)

## Verdict

**Plan B — grown patches only; backdrop not certifiable under the spec's bar.**

Per §3: "Fail → the composite degrades to grown patches only, and this spec's backdrop
sections are marked Plan B, global-coverage style." §3 also states a fail here is itself a
successful spike outcome — the gate did its job, and it is recorded rather than rescued.

The failure is structural, not a pipeline defect. It matches SSCOFS's own published NOS skill
class (~±30 min phase); at weak-current stations, non-tidal residual flow in the nowcast
shifts zero-crossings enough that slack timing is ill-defined for a 0.1–0.3 kn station
regardless of fit quality. The pipeline itself is trusted on separate evidence: byte-parity to
the shipping fit path (Task 5, §"Method" above), the epoch-ms sample contract is what Task 5's
own review caught and fixed rather than silently working around, and the negative control
(Dodd) fails exactly as the physics predicted, not marginally.

## Open question for the owner

Spec §1's "Render channels" amendment draws an honest middle path this spike did not decide:
the backdrop's shipped role is the **speed fill channel** (a per-cell colour raster); timing
semantics (slack, transitability) live with gates and grown patches, not the fill. Read that
way, the 40/53 speed-only pass rate is a live number — but a speed-only certification bar was
not defined anywhere in this spec, so adopting it is the owner's call, not this spike's.

Adopting it would require, at minimum:

1. A defined speed-only certification rule in §4 (which quantity, what threshold, replacing
   or supplementing the five-bar table for backdrop purposes only).
2. Timing semantics explicitly and visibly stripped from the backdrop tier — no slack-state
   colour, no "transitable now" implication from the fill layer, so a user can't read a speed
   ramp as a timing claim near slack (§1 already flags this: "near slack the reference field
   goes uniformly low-ramp and carries no planning signal").
3. Bundle pruning proof. §2/§3 pruning ideas (speed-certified regions only, a per-element
   energy floor) are plausible but **unproven in this spike** — this run fit and scored every
   box element indiscriminately; it never tried certifying a subset and re-measuring bundle
   size against just that subset.
4. An answer for stations too weak to grade at all: `cherry-point`'s 36 nearby elements all
   have published extrema below 0.75 kn, so it has no scoreable speed error under *any* bar,
   five-quantity or speed-only. A speed-only certification rule needs to say what happens to a
   station (and the water around it) that can't be graded because its own current is too weak
   to measure by this method — silently no-data, or certified some other way.

## What would change this

- **A 190-day corpus** (spec §2's Phase B window), to resolve K1/P1 and the other constituent
  pairs this spike's 60-day fits list as unseparable
  (`S2/T2, N2/NU2, 2N2/MU2, S2/K2, K1/P1, MSF/MF, K2/T2` — every one of the 2,004 fits, not
  station-specific). `chs-currents-fit`'s own 210d-vs-60d comparison shows the same mechanism
  moving slack error by roughly 3× at a weak-tidal gate (Dodd: 2.1 → 15.1 min going 210d→60d);
  this spike's 60-day-only run cannot rule out a similar improvement at 190 days, only that it
  wasn't tested.
- **A per-element residual/R² floor** (spec §9's own risk item): mask elements whose variance
  isn't mostly tidal instead of scoring them against a bar they were never going to meet.
- **A defined speed-only certification bar + fill-only render contract**, if the owner picks
  up the open question above rather than accepting Plan B as final.

## Prerequisites executed (2026-08-20)

The owner ruling's two prerequisites (spec §4a certification rule, §10 pruning method) have
both been run against this spike's real 60-day box data. Both PASS. Numbers below are
independently reproducible — neither script recomputes anything from a cached summary.

### Certification geometry (§4a)

`./certify.py` grades the 54 stations in `samples/index.json` (53 scoreable) from
`results/*.json` (see "Results" above),
then classifies every one of the box's 73,550 mesh elements by nearest-scoreable-station
distance. Station verdicts: **40 PASS / 13 FAIL / 1 UNSCOREABLE** (`cherry-point` — no
published extremum above the 0.75 kn significance floor at any nearby element, so it grades
nothing, per spec). At the spec's default D = 3 km:

| status | elements | % of box |
|---|---|---|
| certified (yes) | 22,681 | 30.8% |
| masked (nearest station FAILED) | 4,336 | 5.9% |
| no-data (no scoreable station within D) | 46,533 | 63.3% |

Sensitivity (same station verdicts, D varied): **18.1% certified @ 2 km, 30.8% @ 3 km, 45.5%
@ 5 km.**

Artifacts (gitignored, regenerate with `./certify.py`): `certified/certified.json`,
`certified/certified.geojson`, `certified/CERTIFY.md`.

### Bundle-pruning proof (§10) — PASS

`./prune_proof.py` fits every box element with vectorized numpy-lstsq sizing fits (23-name
shipping basis, not `chs-glue`'s `fitTides` — that label is kept on every line of its output
report on purpose), applies the R² ≥ 0.8 tidal floor and the per-element energy floor, then
extrapolates the surviving elements' measured size to the full render region, capped at the
SSCOFS mesh's own element count (433,410 — the earlier density-only extrapolation in this
README's "Results" section overshot that cap and was called out in review).

At D = 3 km / R² ≥ 0.8 (the spec defaults): 6,319 of the 22,681 certified elements survive
the R² floor — **1.40 MB measured in-box**, extrapolating to **13.25 MB** for the render
region. **PASS against the 40 MB budget**, and PASS at all six D × R² sensitivity
combinations run (D = 2/3/5 km, R² = 0.7/0.8/0.9): range 5.27–19.72 MB, every one well under
40 MB.

Artifact (gitignored, regenerate with `./prune_proof.py`): `certified/PRUNING.md`.

### Owner-visible yield facts

Two things a PASS verdict doesn't say on its own, and that need to be plain before anyone
scopes the fill render layer:

1. **Only 27.9% of D = 3 km-certified elements clear the R² ≥ 0.8 floor.** The painted fill
   ends up covering **≈8.6% of box water** (6,319 of 73,550 elements) — sparse, honest, and
   concentrated where the tide actually dominates the signal. Most of the box is either
   uncertified (no nearby scoreable station), masked (nearest station failed), or certified
   but too weakly tidal to paint.
2. **The energy floor barely prunes on real data.** Surviving elements keep a mean of
   21.3 of 23 possible constituents — the 2%-of-max-amplitude floor is mostly catching noise,
   not trimming a fat basis. That's the conservative direction for a size estimate (it means
   13.25 MB is close to what a real shipping fit would cost, not an optimistic floor), but it
   means constituent-count pruning isn't where the bundle's headroom under 40 MB comes from —
   region certification is.

### What remains before a fill pixel ships (Phase B engineering — pointers, not plans)

  fits) for the elements that survive both certification and the R² floor.
- **Mask + bundle shipping format** — this spike proved the size and geometry, not the
  on-disk/on-wire format the app will actually ship and load.
- **The fill render layer** — #57's channel-2 sibling seam (particle layer ships separately;
  this is the backdrop-colour channel it composites under).
- **No green in the ramp** — the spec status block's guardrail is the render layer's
  responsibility to enforce, not this spike's; nothing here checks it because nothing here
  renders.
