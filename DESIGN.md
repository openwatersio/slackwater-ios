# TestFlight feedback intake design

Research checked 2026-09-13. Scope: ingest TestFlight screenshot and crash feedback into a **separate private GitHub repository**. `slackwater-ios` remains public and contains only service code and this design. Public issue drafting is a later, separately authorized stage.

## Verified Apple and GitHub capabilities

- App Store Connect [webhooks](https://developer.apple.com/documentation/appstoreconnectapi/configuring-webhook-notifications) support `BETA_FEEDBACK_SCREENSHOT_SUBMISSION_CREATED` and `BETA_FEEDBACK_CRASH_SUBMISSION_CREATED`. The [event examples](https://developer.apple.com/documentation/appstoreconnectapi/webhook-events) contain an event ID, timestamp, and `relationships.instance.data` with the feedback resource type and ID; they do **not** contain the full feedback. Configure a webhook for the app with those two event types using `POST /v1/webhooks` (or the App Store Connect UI). A person with Account Holder, Admin, or App Manager access [can manage webhooks](https://developer.apple.com/help/app-store-connect/manage-your-team/manage-webhooks).
- Apple signs the **raw POST body** with HMAC-SHA256. The header is `x-apple-signature: hmacsha256=<hex digest>`; verify it with the configured webhook secret using a constant-time comparison *before* parsing JSON or doing any writes. This is distinct from App Store Connect API authentication: API reads require an [ES256 JWT](https://developer.apple.com/documentation/appstoreconnectapi/generating-tokens-for-api-requests) with `kid`, `aud=appstoreconnect-v1`, and a short expiry (normally at most 20 minutes). A Developer-role key can [read screenshot submissions](https://developer.apple.com/documentation/appstoreconnectapi/beta-feedback-screenshot-submissions) and [crash submissions](https://developer.apple.com/documentation/appstoreconnectapi/beta-feedback-crash-submissions).
- Read the specific resource via `GET /v1/betaFeedbackScreenshotSubmissions/{id}` or `GET /v1/betaFeedbackCrashSubmissions/{id}`. The [screenshot collection fields](https://developer.apple.com/documentation/appstoreconnectapi/get-v1-apps-_id_-betafeedbackscreenshotsubmissions) and [crash collection fields](https://developer.apple.com/documentation/appstoreconnectapi/get-v1-apps-_id_-betafeedbackcrashsubmissions) expose comment, creation time, device model, OS version, email, many device diagnostics, and relationships to build/tester. Request only needed fields and `build`, never `tester` or `email`. The screenshot record exposes image URLs with an [`expirationDate`](https://developer.apple.com/documentation/appstoreconnectapi/betafeedbackscreenshotimage); fetch the bytes promptly, because the URL is not a durable link. Crash feedback has a `crashLog` relationship; Apple exposes [`logText`](https://developer.apple.com/documentation/appstoreconnectapi/betacrashlog/attributes-data.dictionary) through `GET /v1/betaCrashLogs/{id}`. Read build `version` (build number) and its [prerelease version](https://developer.apple.com/documentation/appstoreconnectapi/get-v1-builds-_id_-prereleaseversion) (app version).
- GitHub's [Create an issue](https://docs.github.com/en/rest/issues/issues#create-an-issue) API accepts title, body, and labels in a private repository. The [repository contents API](https://docs.github.com/en/rest/repos/contents#create-or-update-file-contents) can create a small deduplication record. There is no documented REST endpoint to upload an attachment **to an issue**; the documented [release-asset upload API](https://docs.github.com/en/rest/releases/assets#upload-a-release-asset) accepts binary files, and only people with repository read access can [view its private releases](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases). Use private release assets for screenshots and crash logs so those files do not enter Git history. Rotate assets across releases before GitHub's 1,000-assets-per-release limit.
- Cloudflare Workers expose a native [`fetch(request, env)` handler](https://developers.cloudflare.com/workers/runtime-apis/handlers/fetch/), raw request bytes, [Web Crypto](https://developers.cloudflare.com/workers/runtime-apis/web-crypto/) for HMAC and ES256, and [secret bindings](https://developers.cloudflare.com/workers/configuration/secrets/). A dedicated Worker in the existing Cloudflare account keeps feedback credentials separate from the public tides API. Cloudflare [Workers Builds supports a monorepo root directory](https://developers.cloudflare.com/workers/ci-cd/builds/configuration/); point it at this service directory. Its [128 MB memory limit](https://developers.cloudflare.com/workers/platform/limits/) calls for a small per-asset cap. GitHub expects `Content-Length` on release uploads, and Workers [set it for fixed-length bodies](https://developers.cloudflare.com/workers/runtime-apis/request/#set-the-content-length-header): buffer at most 8 MiB per asset, upload one at a time, and record larger assets as omissions. Verify a real upload on the existing paid Workers plan before activation.

Apple's listed webhook types have no separate text-only/email-feedback event. Older TestFlight feedback sent by email is outside this intake; Apple documents that [older clients can send email feedback](https://developer.apple.com/help/app-store-connect/test-a-beta-version/view-tester-feedback). This service does not scrape the UI or parse email. Apple documents [delivery inspection and manual redelivery](https://developer.apple.com/documentation/appstoreconnectapi/webhook-notifications); do not rely on an undocumented automatic retry schedule.

## Flow and trust boundary

`Apple webhook → dedicated Cloudflare Worker → App Store Connect API/image URL → private GitHub issue + private release assets`

1. `POST /testflight-feedback` on the dedicated Worker's HTTPS hostname is the only public endpoint. Read at most 64 KiB from the request stream, verify HMAC over those exact bytes, accept only the two documented event shapes, and ignore authenticated ping/other event types. Construct Apple API URLs from the validated resource type and ID; never fetch a webhook-supplied URL verbatim.
2. Fetch the full submission, its build and prerelease version, and verify the build belongs to the configured Apple app ID. Retain the raw comment and, for crash submissions, the crash log if Apple provides one. Fetch screenshot bytes only over HTTPS from the URL returned by Apple's authenticated API, with caching disabled; enforce the 8 MiB byte cap while reading, not just from `Content-Length`. A missing or oversized asset becomes an explicit private-issue omission, not a public link to an expiring URL.
3. Before writing feedback, `GET /repos/{owner}/{repo}` must confirm the configured destination is the intended **private** repository. Use a fine-grained GitHub token restricted to that repository with Issues: write and Contents: write. The service has no token or code path for the public project repository. Store screenshots/logs as release assets in the private repo, then create one private issue.
4. Return success only after the issue and deduplication record are complete. Log event kind, opaque IDs, outcome, and error class only. Never log request/response bodies, comments, crash logs, screenshot URLs/bytes, or GitHub API error bodies that may echo them. Keep feedback in memory only during the request; do not configure Cloudflare logs, traces, or analytics to capture payloads, and add no KV/R2/D1 store. Do not acknowledge early and defer ingestion with `waitUntil`, since [background execution is bounded](https://developers.cloudflare.com/workers/platform/limits/) and would hide failures from Apple's delivery response.

**Data copied to private GitHub:** raw tester comment; screenshot bytes or crash-log text when available; Apple feedback ID/type, app/build IDs, app version/build number, submission time, device model, and OS version. **Data deliberately omitted:** Apple email, tester relationship/name, locale, time zone, battery, disk, network, watch pairing, uptime, and other device telemetry. The comment, screenshot, and crash log themselves can contain PII; private repository access and GitHub notifications must be limited accordingly. Secrets (`APPLE_WEBHOOK_SECRET`, Apple key ID/issuer/private key, `GITHUB_TOKEN`) are [Cloudflare secret bindings](https://developers.cloudflare.com/workers/configuration/secrets/), never committed. Apple app ID and private repo name are ordinary Worker environment variables. GitHub is the durable copy; Apple remains the source of provenance.

## Idempotency and failure behavior

Use `source_key = <Apple app ID>:<screenshot|crash>:<Apple submission ID>`; webhook event ID is recorded for audit but is **not** the deduplication key. Before creating an issue, create `intake/<SHA-256(source_key)>.json` in the private repository using GitHub Contents API **create** semantics (no replacement SHA). It contains only source key, event ID, phase, and eventual issue number. The phases are `reserved → creating → complete`; release assets are uploaded before `creating`, with deterministic names so asset retries can find existing uploads. A reserved record can resume asset work. Only the request whose blob-SHA-conditional update from `reserved` to `creating` succeeds may call Create an issue; a conflict must refetch the record, never make another create call. Write `creating` **before** calling Create an issue. If that call or its response is ambiguous, never automatically call it again: leave the record in `creating` for manual reconciliation against the private issue marker. This conservative exception trades immediate completion for avoiding duplicate issues. A small reconciliation command can inspect incomplete records, Apple deliveries, and private issues without storing raw feedback elsewhere. The implementation must exercise concurrent claims against GitHub before claiming this guarantee; if create-if-absent is not atomic enough, replace the claim with a tiny transactional unique-key store containing IDs/phases only.

Transient failures before `creating` return a retryable 5xx. An invalid signature returns 401; invalid/unrelated payloads return 4xx or a harmless 2xx as appropriate. For a completed record, redelivery returns 2xx without side effects. A record stuck in `creating` is surfaced to an operator without logging feedback content; manually bind the existing issue number or explicitly resume after verifying no issue was created.

## Private issue contract (v1)

Neutral title: `[TestFlight screenshot] 1.2.3 (456) · <short source-key hash>` (or `crash`). Labels: `testflight-feedback`, `source:screenshot`/`source:crash`, `needs-triage`, and `version:1.2.3`; keep the build number in the body to avoid a label per build. Pre-create labels, verify them after issue creation, and repair any GitHub silently drops before marking the intake complete.

The body starts with an HTML comment delimited by `<!-- testflight-feedback:v1` and `-->`, containing JSON fields `source_key`, `apple_event_id`, `apple_app_id`, `apple_submission_id`, `apple_build_id`, `app_version`, `build_number`, `submitted_at`, `device_model`, `os_version`, `private_asset_ids`, `asset_omissions`, `triage_status: "needs-triage"`, `related_private_issue_numbers: []`, and `public_issue_url: null`. Then show the **verbatim** tester comment in a Markdown code block (with a safe dynamic fence, so mentions and Markdown are not interpreted), private links to screenshot/crash-log assets, and a short triage section for related private reports. No raw feedback appears in the title, labels, GitHub commit messages, or public repository.

The later triage agent can read this versioned block, compare private reports with public issues, write a clean reproduction-oriented public issue, and update `public_issue_url` plus related-report links **only in private issues**. It must review/redact text and images before any public write. The intake service does not implement or authorize that step.

## Proposed project shape and implementation steps

Place the small TypeScript service under `services/testflight-feedback/` in this public repo. Cloudflare Workers Builds uses that directory as its project root, matching the separate-Worker pattern already used in `openwaters.io`:

```text
services/testflight-feedback/
  src/index.ts              # Worker fetch handler and HTTP responses
  src/apple.ts               # HMAC verification, JWT, feedback/build reads
  src/github.ts              # private-repo guard, claim, assets, issue
  src/ingest.ts              # one-submission flow and issue formatting
  test/ingest.test.ts        # Node built-in test runner, mocked API calls
  package.json              # TypeScript checks and Wrangler commands
  README.md                 # setup, secrets, and operator recovery
  wrangler.jsonc            # Worker name, entry point, compatibility date
```

1. Create the private feedback repository, labels, a dedicated GitHub token, and an Apple Developer-role API key; register the Apple webhook with a separate random HMAC secret. Keep setup commands and environment variable names in the service README, with no secret values.
2. Implement the webhook function and Apple client. Use raw-body HMAC verification, typed validation of the two event shapes, ES256 API JWTs, exact feedback/build reads, and app-ID verification.
3. Implement the private GitHub guard, source-key claim/phases, screenshot/crash-log release assets, and the versioned issue body. Keep all GitHub writes aimed at one configured private repo.
4. Add focused tests for bad signature, wrong app, duplicate/concurrent delivery, missing asset, and ambiguous issue-create response. Exercise the Worker with `wrangler dev`, then test a real Apple webhook ping and a private-repo end-to-end submission before enabling production traffic; inspect only sanitized logs.
5. Connect a dedicated Worker to this repository through Workers Builds, rooted at `services/testflight-feedback/` and deployed from `main`; disable preview URLs and bind production secrets only to this Worker. Register its generated HTTPS URL with Apple. Document delivery inspection, manual redelivery, stuck-claim reconciliation, asset retention/deletion, and the rule that the private feedback repository must never be made public.

No triage agent, public issue creation, polling scheduler, database, or dashboard is part of this implementation.
